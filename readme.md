# Blog AI

An HTTP API for creating, reviewing, and publishing blog posts with AI-assisted
draft generation. Drafts are generated by a Mastra agent, stored in PostgreSQL,
and only become publicly visible after approval.

## Stack

- Node.js 24 with native HTTP server and ES modules
- PostgreSQL 17
- Mastra with the `google/gemini-3.5-flash-lite` model
- Native Node.js test runner and Supertest
- Postgrator for database migrations
- Oxlint and Oxfmt for code quality
- Docker Compose for the API and PostgreSQL infrastructure

## How It Works

1. `POST /posts/draft` sends an idea to the Mastra post-writer agent.
2. The generated title and Markdown content are saved as an unpublished draft.
3. `PATCH /posts/:id/approve` approves and publishes the post immediately.
4. `DELETE /posts/:id/reject` rejects the post and removes it from public lists.
5. Public read endpoints return only posts that are approved, not rejected, and
   already past their `published_at` timestamp.

The application is intentionally small. Routing, request parsing, persistence,
and the API layer are implemented in `src/` without a web framework.

## Environment Files

The repository includes `.env.exemple` as a template. Create separate files for
local development and tests:

```bash
cp .env.exemple .env.local
cp .env.exemple .env.test
```

Set the values in both files as appropriate:

| Variable                       | Purpose                                                | Local example                                      |
| ------------------------------ | ------------------------------------------------------ | -------------------------------------------------- |
| `API_HOST`                     | HTTP server bind address                               | `127.0.0.1`                                        |
| `API_PORT`                     | HTTP server port                                       | `8080`                                             |
| `API_PROTOCOL`                 | Protocol displayed in logs and Swagger server metadata | `http`                                             |
| `API_KEY`                      | Bearer key required by `GET /posts?include=all`        | `local-secret`                                     |
| `GOOGLE_GENERATIVE_AI_API_KEY` | Google Generative AI credential used by Mastra         | `your-google-key`                                  |
| `DATABASE_URL`                 | PostgreSQL connection string                           | `postgres://postgres:postgres@localhost:5432/blog` |

Do not commit `.env.local` or `.env.test`. The `.gitignore` excludes environment
files, while `.env.exemple` remains tracked as the setup template.

Use a separate test database whenever possible. The integration and end-to-end
tests run `TRUNCATE TABLE posts`, so pointing `.env.test` at a database with
important data can destroy that data.

## Local Development

### 1. Install and configure

```bash
npm install
cp .env.exemple .env.local
cp .env.exemple .env.test
```

Edit both files with valid credentials and connection strings.

### 2. Start PostgreSQL

To start only the database container:

```bash
npm run infra:up
```

The Compose database uses:

- Host: `localhost`
- Port: `5432`
- Database: `blog`
- User: `postgres`
- Password: `postgres`

### 3. Apply migrations

```bash
npm run migrate:up
```

### 4. Start the API

```bash
npm run dev
```

The development server uses Node's watch mode and loads `.env.local`. It is
available at `http://127.0.0.1:8080` when using the example values above.

Stop the database when it is no longer needed:

```bash
npm run infra:down
```

## Docker

The Compose stack contains:

- `api`: the Node.js application on port `8080`
- `postgres`: PostgreSQL 17 on port `5432`
- `postgres_data`: a persistent Docker volume

Start the complete stack in the foreground:

```bash
npm run docker:up
```

Or start it in the background:

```bash
docker compose up --build -d
```

The API container loads `.env.local`, then overrides its network settings and
database connection to use the Compose service name `postgres`. Migrations are
not applied automatically. With the containers running, apply them from the
host using:

```bash
npm run migrate:up
```

Stop the complete stack with:

```bash
npm run docker:down
```

The Docker image is production-oriented: it installs production dependencies,
copies only `src/`, runs as a non-root `app` user, and exposes port `8080`.
Migrations must therefore be handled separately from the image.

## API

All successful responses use a `{ "data": ... }` envelope. Errors use a
`{ "message": "..." }` envelope.

### `GET /posts`

Returns published posts only.

To include drafts and other non-public posts, use:

```bash
curl -H "Authorization: Bearer $API_KEY" \
  "http://127.0.0.1:8080/posts?include=all"
```

The `include=all` variant returns `403 Forbidden` without a valid Bearer token.

### `GET /posts/:id`

Returns one published post. A draft, rejected post, scheduled post, or unknown
ID returns `404`.

### `POST /posts/draft`

Generates and stores a draft using the AI agent:

```bash
curl -X POST http://127.0.0.1:8080/posts/draft \
  -H "Content-Type: application/json" \
  -d '{"idea":"How to test Node.js APIs with Supertest"}'
```

The request body must contain an `idea` value. Generation or persistence errors
return `500` with the original error message.

### `PATCH /posts/:id/approve`

Sets `approved_at` and `published_at` to the current time, publishing the post.

### `DELETE /posts/:id/reject`

Sets `rejected_at` to the current time and clears `approved_at` and
`published_at`.

### API documentation

- Swagger UI: `http://127.0.0.1:8080/api/docs`
- OpenAPI JSON: `http://127.0.0.1:8080/api/docs/json`

The Swagger UI loads its assets from `unpkg.com`, so an internet connection is
needed to render the interface in a browser.

## Database

The `posts` table is created by
`src/database/migrations/001.do.create-posts-table.sql` and contains:

| Column         | Description                                            |
| -------------- | ------------------------------------------------------ |
| `id`           | Nanoid-based primary key, up to 21 characters          |
| `title`        | Generated or supplied post title                       |
| `content`      | Markdown post content                                  |
| `published_at` | Publication time; `NULL` for drafts and rejected posts |
| `created_at`   | Creation time                                          |
| `approved_at`  | Approval time; `NULL` until approved                   |
| `rejected_at`  | Rejection time; `NULL` unless rejected                 |

Apply all pending migrations:

```bash
npm run migrate:up
```

Revert the database to migration level zero:

```bash
npm run migrate:down
```

The down migration drops the `posts` table. Use it only when intentionally
resetting the database.

## Tests

Unit tests run without a database and cover JSON parsing, routing, and Bearer
token validation.

Integration tests exercise the PostgreSQL repository and require:

1. A valid `.env.test`.
2. A running PostgreSQL instance.
3. The `posts` migration applied to the test database.

End-to-end tests use Supertest against the in-process HTTP server. Most draft
generation coverage injects a stub into `createApp`, so it does not call the AI
provider. The database-backed API tests still require PostgreSQL and a migrated
test database.

Run the full suite with:

```bash
npm test
```

Tests clean up rows with `TRUNCATE TABLE posts` and close the shared PostgreSQL
pool after database-backed suites.

## Code Standards And Commits

- Use ES modules and the existing Node.js patterns.
- Keep routing in `src/routes`, persistence in `src/repositories`, business
  behavior in `src/services`, and shared HTTP/database utilities in their
  respective directories.
- Run `npm run lint` and `npm run format:check` before opening a change.
- Run `npm test` when changing behavior, persistence, or routes.
- Keep API responses and database field names consistent with the existing
  snake_case contract.

Lefthook installs Git hooks through `npm install`'s `prepare` script:

- `pre-commit`: runs Oxlint and Oxfmt on staged JavaScript files through
  `lint-staged`.
- `commit-msg`: validates the message with Commitlint.

Use the interactive helper for a valid commit message:

```bash
npm run commit
```

Supported commit types include `feat`, `fix`, `refactor`, `perf`, `test`,
`docs`, `style`, `build`, `ci`, `chore`, and `revert`. The resulting format is:

```text
type(scope): description
```

## Important Limitations

- Only `GET /posts?include=all` is protected by `API_KEY`; approval, rejection,
  and draft creation endpoints currently have no API-key check.
- Request validation is intentionally minimal. Invalid JSON is surfaced as a
  server error by the draft route, and the route does not validate a missing
  `idea` before calling the service.
- Public posts are published immediately when approved; there is no scheduling
  workflow beyond the database field and query condition.
- There is no authentication or authorization system beyond the single Bearer
  key used for the administrative list variant.
- Swagger metadata and some generated content descriptions are currently in
  Portuguese, while this README is in English.
